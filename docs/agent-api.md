# pulse_agent — API для систем-клиентов

pulse_agent отвечает на вопросы об инфраструктуре: состояние сервисов и кластера, ошибки,
алерты, что и когда менялось, следы заказа или клиента в логах. Данные берёт живьём из
[pulse](https://github.com/mechta-market/pulse) (Kubernetes, Prometheus, Loki, Alertmanager,
GitHub, kusec, ruto) через LLM с инструментами. Ответ синхронный: от нескольких секунд до
`AGENT_TIMEOUT` (5 минут; обычно 10–30 с, поиск по номеру заказа — до минуты).

Клиенты: Telegram-бот (`pulse_bot`), service-desk, разбор алертов — у каждой системы свой ключ.

## Доступ

`Authorization: Bearer <ключ системы>`. Ключи выдаются по системе (env `API_KEYS` в kusec):
по ключу известно, кто спрашивает, — журнал, метрики и свои беседы. Без ключа или с чужим — `401`.

## POST /v1/ask

```json
{
  "question": "что с caravan?",
  "conversation_id": "SD-12345",
  "reset": false,
  "user": {"id": "ivanov", "name": "Иван Иванов"},
  "format": "json",
  "charts": "all",
  "trace": false
}
```

| поле | | |
|---|---|---|
| `question` | обязательно | вопрос, до 4000 символов |
| `conversation_id` | | беседа в системе клиента (тикет, чат): агент помнит последние 10 вопросов и ответов, уточнения вида «а за сутки?» понимает; пусто — вопрос без истории. Беседы разных систем не пересекаются. История — в памяти сервиса, после часа тишины или рестарта начинается заново |
| `reset` | | забыть историю беседы перед вопросом |
| `user` | | кто спросил в системе клиента: пишется в журнал (позже — разграничение доступа) |
| `format` | | `telegram` (по умолчанию) — Markdown для Telegram; `markdown`; `plain` — без разметки; `json` — ответ по полям в `result` (схема по умолчанию) |
| `response_schema` | | своя JSON Schema ответа — RPC: `result` приходит строго по ней (см. ниже); задана — формат `json` |
| `charts` | | `all` (по умолчанию) — картинка и данные; `png` — только картинка; `data` — только данные (клиент рисует сам); `none` — без графиков |
| `trace`, `trace_output_limit` | | ход разбора: вызовы инструментов pulse (ответ каждого — до `trace_output_limit` байт, по умолчанию 2000); как их видела модель — персональные данные токенами `pii:<вид>:<код>` |

Неизвестные поля — `400` (опечатка не должна молча менять поведение).

Персональные данные (телефоны, email, ИИН, id клиента, ФИО из ответов сервисов) модель видит
только токенами: агент прячет их до модели и возвращает в ответ настоящие значения. Клиенту
ничего делать не нужно — в `answer` и `result` данные как есть.

### Своя схема ответа (RPC)

Система задаёт, какие поля ей нужны, — `result` приходит строго по схеме, без разбора текста:

```json
{
  "question": "что по заказу 41314079?",
  "conversation_id": "SD-12345",
  "response_schema": {
    "type": "object",
    "properties": {
      "found": {"type": "boolean", "description": "нашлись ли следы заказа в логах"},
      "last_status": {"type": "string", "description": "последний статус заказа из логов"},
      "last_event_at": {"type": "string", "description": "время последнего события, RFC3339"},
      "services": {"type": "array", "items": {"type": "string"}, "description": "сервисы, в логах которых есть заказ"},
      "problem": {"type": "string", "description": "что пошло не так, если что-то пошло"}
    },
    "required": ["found", "services"]
  }
}
```

```json
{
  "answer": "{\"found\":true,\"last_status\":\"COMPLETED\",…}",
  "result": {
    "found": true,
    "last_status": "COMPLETED",
    "last_event_at": "2026-09-24T15:31:30+05:00",
    "services": ["delivery", "mb-broker", "orders-center"],
    "problem": "Halyk не подтвердил COMPLETED: задача waitForMerchantComplete не создана"
  },
  …
}
```

- Схема — обычная JSON Schema с корнем `{"type": "object"}`. Смысл полей агент берёт из их
  имён и `description` — описывайте поля, как описали бы их человеку (в каких единицах число,
  в каком формате время).
- Поля не из `required` приходят `null`, когда данных нет: агент не выдумывает значения.
  Обязательные поля заполняются всегда — делайте обязательным только то, что есть всегда.
- Числовые поля — в единицах из имени или описания поля (`memory_mb`, «задержка в
  миллисекундах»), иначе — как в источнике (байты, секунды, доли). Время — RFC3339 с поясом.
- Поддерживаются `object`, `array`, `string`, `number`, `integer`, `boolean`, `enum`, `anyOf`
  (`oneOf` понимается как `anyOf`), `$defs`; до 5 уровней вложенности и 100 полей. Схему, которую
  модель принять не может, агент отвергает с `400 invalid_request` и объяснением.
- `answer` в этом режиме — тот же JSON строкой; история беседы и уточнения работают как обычно.

### Ответ

```json
{
  "answer": "caravan деградировал: задержка выросла…",
  "result": {
    "summary": "caravan деградировал: задержка p95 выросла в 30 раз, отказов нет",
    "status": "degraded",
    "severity": "medium",
    "services": [{"name": "caravan", "status": "degraded", "note": "p95 650 мс против 19 мс час назад"}],
    "facts": [
      {"text": "Задержка p95 — 650 мс против 19 мс час назад", "time": "2026-09-25T14:58:00+05:00", "service": "caravan"},
      {"text": "За сутки деплоев и смены конфигурации не было", "time": null, "service": null}
    ],
    "next_steps": ["Проверить, какие запросы замедлились"],
    "unavailable_sources": []
  },
  "incomplete": "",
  "charts": [
    {
      "title": "Задержка p95 caravan за 24 часа",
      "type": "line",
      "unit": "seconds",
      "png": "iVBORw0KGgo…",
      "data": {"series": [{"name": "caravan", "points": [{"x": "2026-09-25T14:00:00+05:00", "y": 0.65}]}]}
    }
  ],
  "duration_ms": 19210,
  "steps": 4,
  "tool_calls": 4,
  "usage": {"input_tokens": 19191, "cached_tokens": 15360, "output_tokens": 410, "reasoning_tokens": 120}
}
```

- `answer` — текст ответа в запрошенном формате; при `format=json` собран из `result`
  (вывод, факты, что дальше) — пригоден для показа человеку как есть.
- `result` — JSON-ответ: по `response_schema` системы, иначе при `format=json` — по схеме по
  умолчанию (поля ниже); при текстовом формате — `null`. Может быть `null` и при `json`, если
  разбор оборван (`incomplete`) и модель не успела выдать JSON — тогда есть только `answer`.
  Схема по умолчанию:
  - `status` — состояние того, о чём спросили: `ok`, `degraded`, `down`, `not_found`
    (сервис, заказ или запись не найдены), `unknown` (данных не хватило);
  - `severity` — `none`, `low`, `medium`, `high`, `critical`;
  - `services[]` — сервисы, о которых ответ (имена каталога pulse), `status` — как выше;
  - `facts[]` — факты, на которых основан вывод; `time` — RFC3339 с поясом (Asia/Almaty) или
    `null`, `service` — имя сервиса или `null`;
  - `next_steps[]` — что проверить или сделать; `unavailable_sources[]` — источники, которые
    не ответили (часть картины отсутствует). Списки — всегда массивы, пустые — `[]`.
- `incomplete` — разбор закончен досрочно: `timeout` (время), `tool_calls` (лимит вызовов),
  `output` (ответ модели оборван). Пусто — ответ полный.
- `charts[]` — графики, если агент решил, что они нужны (динамика за период, сравнение
  сервисов; до 3). `png` — PNG в base64 (тёмная тема), `data` — ряды, по которым нарисовано:
  у `line` `x` — время RFC3339, у `bar` — подпись категории; `y` — в единицах `unit` как
  пришло из источника (`bytes`, `ratio`, `seconds`, `cores`, `rps`, `count`).

## POST /v1/reset

`{"conversation_id": "SD-12345"}` → `{"reset": true}` — забыть историю беседы.

## POST /v1/eval

Прогон эталонных вопросов агента (вшиты в образ, ~20 типовых вопросов с проверками поведения) —
для систем из `EVAL_CLIENTS` (бот: команда `/eval` для админов). `{"only": ["order-found"]}` —
часть набора, `{}` — все. Синхронно, до нескольких минут. Ответ: `text` — таблица (что прошло,
что сломалось относительно эталона, время, токены), `report` — отчёт целиком. Одновременно идёт
один прогон: второй — `409 busy`. Системе не из `EVAL_CLIENTS` — `403 forbidden`.

## Контекст беседы

Беседа — `conversation_id` системы (чат Telegram, тикет). У неё есть **заметки**: что участники
попросили запомнить («мы команда доставки, нас интересуют caravan и notifire»). Заметки идут модели
с каждым вопросом этой беседы (до 2000 символов). В вопросе с `conversation_id` модель сама
сохраняет заметки и управляет подписками и приглушениями по просьбе («запомни…», «не присылай про caravan до
понедельника», «что у нас приглушено?») — клиенту ничего делать не нужно.

- `GET /v1/chat?conversation_id=…` → `{"conversation_id", "notes", "notes_updated_at", "notes_updated_by"}`
- `PUT /v1/chat/notes` `{"conversation_id", "notes", "user": {"id", "name"}}` — перезаписать (пусто — забыть)

## Уведомления наблюдателя

Агент сам следит за кластером: **алерты** разбирает сразу, **выкатки** — через 15 минут после них
(и только если сервису стало нехорошо; здоровые выкатки — молча). Разбор — как ответ на вопрос:
что случилось, насколько серьёзно, причина, что сделать. Один и тот же алерт сервиса — не чаще
раза в 6 часов. Уведомления общие; каждая беседа читает ленту сама и видит, что у неё приглушено.

- `GET /v1/notifications?conversation_id=…&limit=20` — новые уведомления беседы (после
  подтверждённых), по порядку. **Первый вызов подписывает беседу с текущего места** — ответ пустой,
  старое не приходит.

  ```json
  {"items": [{
    "id": 42, "at": "2026-09-26T17:35:11+05:00", "kind": "deploy", "service": "caravan", "key": "cac1a18",
    "severity": "warning", "title": "caravan: после выкатки 8% сбоев в выдаче",
    "text": "- с 17:21 сбои выросли с 0 до 8%…", "investigated": true, "muted_by": null
  }]}
  ```

  `kind` — `alert` | `deploy`; `severity` — `critical` | `warning` | `info`; `text` — Markdown как
  у формата `telegram`; `investigated: false` — сигнал как есть, без разбора (лимит разборов в час
  или разбор не удался). `muted_by` — id приглушения беседы: такое уведомление не показывать, но
  подтвердить. `not_subscribed: true` — у беседы есть подписки, и уведомление ни под одну не
  подходит: тоже не показывать, но подтвердить.
- `POST /v1/notifications/ack` `{"conversation_id", "last_id"}` — беседа получила всё до `last_id`
  включительно (и приглушённые). Не подтвердили — придёт снова (после рестарта клиента ничего не теряется).

### Подписки

Что присылать беседе. Нет подписок — приходит всё; есть — только подходящее хотя бы под одну.
Приглушения действуют поверх подписок.

- `POST /v1/subscriptions` `{"conversation_id", "service", "kind", "min_severity", "note", "user"}` —
  пустое поле — любое; `min_severity` — `info` | `warning` | `critical` (не ниже). Ответ — подписка
  (`id`, `service`, `kind`, `min_severity`, `note`, `created_at`, `created_by`).
- `GET /v1/subscriptions?conversation_id=…` → `{"subscriptions": […]}`
- `DELETE /v1/subscriptions/{id}?conversation_id=…` — убрать; последнюю убрали — снова приходит всё.

Словами в беседе («присылайте нам только про caravan и notifire», «только критичные») модель
подписывает беседу сама.

### Приглушения

- `POST /v1/mutes` `{"conversation_id", "notification_id", "service", "kind", "key", "duration", "note", "user"}`
  — не присылать в эту беседу: по уведомлению (`notification_id` — его сервис; кнопка под
  уведомлением) и/или по полям; пустое поле — любое. `duration` — `30m`, `2h`, `1d`, `7d`; пусто —
  навсегда. Ответ — приглушение (`id`, `service`, `kind`, `key`, `until`, `note`, `created_at`, `created_by`).
- `GET /v1/mutes?conversation_id=…&muted_limit=10` → `{"mutes": [… "suppressed": 3], "muted": [уведомления]}`
  — действующие приглушения (сколько уже скрыли) и последние скрытые уведомления.
- `DELETE /v1/mutes/{id}?conversation_id=…` — снять приглушение: уведомления снова приходят.

Без хранилища у агента (`PG_DSN` пуст) ручки ленты, приглушений и заметок отвечают `503 unavailable`.

## Ошибки

`{"code": "…", "error": "…"}`:

| статус | code | |
|---|---|---|
| 400 | `invalid_request` | невалидный JSON, неизвестное поле, пустой вопрос, неизвестный `format`/`charts` |
| 401 | `unauthorized` | нет ключа или ключ неизвестен |
| 403 | `forbidden` | ручка не для этой системы (`/v1/eval` вне `EVAL_CLIENTS`) |
| 404 | `not_found` | нет такого приглушения или подписки в беседе, нет уведомления `notification_id` |
| 409 | `busy` | в этой беседе ещё идёт разбор предыдущего вопроса (один вопрос за раз на беседу) |
| 503 | `canceled` | клиент закрыл соединение или сервис перезапускается — повторить |
| 503 | `unavailable` | лента, приглушения и заметки — у агента нет хранилища |
| 504 | `timeout` | разбор не уложился в `AGENT_TIMEOUT` |
| 500 | `internal` | LLM или pulse недоступны и т.п. |

Таймаут клиента — не меньше 6 минут (разбор до 5 минут, ответ приходит целиком).
