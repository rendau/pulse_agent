Порядок: resolve_service → get_service_snapshot (один раз; window — по вопросу, по умолчанию 1h) →
если похоже на последствие изменений — get_timeline сервиса → при необходимости query_logs
(level=error) и query_metrics.

Как читать снапшот:
- health — по фиксированным правилам; summary_hints — готовые выводы: опирайся на них, не пересказывай весь ответ.
- metrics — текущее значение против часа назад и вчера, anomaly — заметное отклонение. error_rate — сбои
  сервиса; rejected_rate — отказы по делу (не найдено, неверный запрос или код): это не сбой, резкий
  рост — повод посмотреть, кто шлёт такие запросы. public_* — трафик через gateway: расхождение с
  внутренними метриками само по себе сигнал.
- pods (готово/всего, рестарты, проблемы), recent_events (OOM, рестарты, выкатки), alerts, top_errors — паттерны ошибок в логах.
- self_reported — что сервис сообщает о себе сам (есть у сервисов с манифестом): зависимости со
  статусом и affects (что ломается, когда она недоступна), показатели (gauges), объекты (entities:
  сколько в каждом статусе, stuck — дольше порога, oldest_s — время в текущем статусе, не с создания).
  stale — отчёт устарел: фоновая проверка в сервисе встала.
- Причина у соседа (зависимость в self_reported не ok — подсказка «подробности — у сервиса X», ошибки
  в логах указывают на неё или вопрос про связь с ней) — загляни к нему сам, не советуй человеку:
  service зависимости → его снапшот (нет service — соседа в каталоге нет, target не угадывай); какие
  именно объекты, базы, запросы сбоят — ручка из его diagnostic_endpoints (get_service_info соседа →
  call_service_endpoint). Один шаг по графу, 1–2 соседа.
- «Сколько объектов сейчас, есть ли застрявшие» — сначала self_reported.entities, за подробностями —
  ручки сервиса (навык service_card).
- «Когда началось» — query_metrics с metric_id из снапшота и окном побольше.

В ответе — отклонения и то, что относится к вопросу; нормальные метрики не перечисляй.
